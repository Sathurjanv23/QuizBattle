# QuizBattle 2.0 Wire Protocol Specification

## 1. Transport & Framing Rules

- **Transport**: TCP stream (default port: `5000`)
- **Discovery**: UDP broadcast/listen (default port: `5001`)
- **Framing Delimiter**: Newline (`\n`, ASCII 0x0A)
- **Encoding**: UTF-8
- **Maximum Frame Size**: **65,536 bytes (64 KiB)**.
  - Sockets or channels that receive a line exceeding 64 KiB before a newline character MUST reject the frame, discard the buffer, and return an `ERROR` message (`FRAME_TOO_LARGE`).
- **TCP Stream Handling & Buffer Fragmentation**:
  - TCP is an arbitrary stream of bytes; a single `read()` call may deliver a partial JSON object or multiple concatenated JSON objects.
  - Implementations must buffer bytes until `\n` is encountered.
  - Once `\n` is found, the substring preceding `\n` is parsed as a single JSON message. The remaining bytes stay in the buffer for the next frame.

---

## 2. Protocol Envelope Format

Every message on the wire is a single-line JSON object:

```json
{"type":"<MESSAGE_TYPE>","requestId":"<OPTIONAL_UUID>","payload":{ ... }}
```

### Envelope Fields:
| Field | Type | Required | Description |
|---|---|---|---|
| `type` | String | **Yes** | Protocol event or command enum name (e.g. `CONNECT`, `CREATE_ROOM`, `QUESTION`). |
| `requestId` | String | *Optional* | Unique correlation identifier generated by sender for request-response pairing. |
| `payload` | Object | *Optional* | Structured data payload specific to the message `type`. |

---

## 3. Security Invariants

1. **Untrusted Client**: The client NEVER sends authoritative game data such as player scores or arbitrary target `playerId`.
2. **Session Association**: The server maps each socket connection to an internal `ClientSession`. On `CONNECT`, the server assigns/authenticates the player and stores this state in the session.
3. **Action Authorization**: When a client requests `CREATE_ROOM`, `JOIN_ROOM`, `START_QUIZ`, or `ANSWER`, the server derives the actor's identity solely from the socket's `ClientSession`.

## 4. Message Catalog & Payloads

### 4.1 Connection Lifecycle

#### `CONNECT` (Client -> Server)
Initiates handshake and requests session binding.
```json
{"type":"CONNECT","requestId":"req-1","payload":{"username":"CyberNinja"}}
```

#### `CONNECTED` (Server -> Client)
Confirms successful connection and assigns authoritative `playerId`.
```json
{"type":"CONNECTED","requestId":"req-1","payload":{"playerId":"usr-9481","username":"CyberNinja","protocolVersion":"2.0"}}
```

---

### 4.2 Room Management (Member 2 Specification)

#### `CREATE_ROOM` (Client -> Server)
Requests server to generate a unique room code and register the creator as host.
```json
{"type":"CREATE_ROOM","requestId":"req-2","payload":{"roomName":"Java Masters","maxPlayers":8}}
```

#### `ROOM_CREATED` (Server -> Client)
Server responds with authoritative 6-character room code (e.g. `QB42KD`) and assigns host.
```json
{"type":"ROOM_CREATED","requestId":"req-2","payload":{"roomId":"QB42KD","roomCode":"QB42KD","roomName":"Java Masters","maxPlayers":8,"hostPlayerId":"usr-9481"}}
```

#### `JOIN_ROOM` (Client -> Server)
Client requests to join room using 6-character code (or `room-default`).
```json
{"type":"JOIN_ROOM","requestId":"req-3","payload":{"roomCode":"QB42KD"}}
```

#### `ROOM_JOINED` (Server -> Client)
Confirms player admission into the room.
```json
{"type":"ROOM_JOINED","requestId":"req-3","payload":{"roomId":"QB42KD","roomCode":"QB42KD","roomName":"Java Masters"}}
```

#### `LEAVE_ROOM` (Client -> Server)
Requests to depart the current room.
```json
{"type":"LEAVE_ROOM","requestId":"req-4","payload":{"roomId":"QB42KD"}}
```

#### `ROOM_LEFT` (Server -> Client)
Confirms departure from room.
```json
{"type":"ROOM_LEFT","requestId":"req-4","payload":{"roomId":"QB42KD","roomCode":"QB42KD"}}
```

#### `ROOM_STATE` (Server -> Client Broadcast)
Broadcast to all room members whenever a player joins, departs, disconnects, or when host changes.
```json
{
  "type":"ROOM_STATE",
  "payload":{
    "roomId":"QB42KD",
    "roomCode":"QB42KD",
    "roomName":"Java Masters",
    "host":"CyberNinja",
    "hostPlayerId":"usr-9481",
    "state":"LOBBY",
    "playerCount":2,
    "players":[
      {"playerId":"usr-9481","username":"CyberNinja","score":0,"isHost":true,"role":"HOST"},
      {"playerId":"usr-3312","username":"PixelCoder","score":0,"isHost":false,"role":"PLAYER"}
    ]
  }
}
```

---

### 4.3 Quiz Flow

#### `START_QUIZ` (Client -> Server)
Must be issued by the room host. Rejected with `FORBIDDEN` if issued by non-host.
```json
{"type":"START_QUIZ","requestId":"req-5","payload":{"roomId":"QB42KD"}}
```

#### `QUESTION` (Server -> Client Broadcast)
Sent to all room participants when a question begins. Correct answer index is masked.
```json
{
  "type":"QUESTION",
  "payload":{
    "questionId":"q-101",
    "text":"What is the primary difference between TCP and UDP?",
    "options":["TCP is connection-oriented; UDP is connectionless","UDP guarantees ordering","TCP is layer 1","UDP requires handshake"],
    "timeLimitSeconds":20,
    "pointValue":100
  }
}
```

#### `ANSWER` (Client -> Server)
Participant submits selected multiple-choice index.
```json
{
  "type":"ANSWER",
  "requestId":"req-6",
  "payload":{
    "questionId":"q-101",
    "selectedOptionIndex":0
  }
}
```

#### `ANSWER_RESULT` (Server -> Client)
Direct feedback to the answering participant.
```json
{
  "type":"ANSWER_RESULT",
  "requestId":"req-6",
  "payload":{
    "questionId":"q-101",
    "correct":true,
    "pointsAwarded":100,
    "currentTotalScore":100
  }
}
```

---

### 4.4 System Diagnostics & Error Handling

#### `ERROR` (Server -> Client)
Structured error envelopes:
```json
{"type":"ERROR","requestId":"req-3","payload":{"code":"ROOM_NOT_FOUND","message":"Room 'NONEX1' does not exist"}}
```
Common error codes:
- `UNAUTHORIZED`: Attempting game actions before `CONNECT` handshake.
- `ROOM_NOT_FOUND`: Room code does not exist.
- `ROOM_FULL`: Room capacity exceeded.
- `FORBIDDEN`: Non-host attempting `START_QUIZ`.
- `MALFORMED_MESSAGE`: Unparseable JSON.
- `FRAME_TOO_LARGE`: Line exceeded 64 KiB cap.

#### `PING` / `PONG`
Heartbeat diagnostic exchange:
```json
{"type":"PING","requestId":"hb-1"}
{"type":"PONG","requestId":"hb-1"}
```
